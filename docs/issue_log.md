## #1 Noetic 没有 cartographer 二进制包

**核实**：拉官方源与清华镜像的 `focal/main/binary-amd64/Packages.gz`（各 3728 个包），
`grep -ic cartographer` 均为 **0**；索引本身有效（能查到 slam-karto / rtabmap / teb）。

**修法**：`docs/wsl_setup.md` 里从安装命令删掉该包，改为"需源码编译"的说明；
并把"一条 apt 装一堆"拆成**逐个安装**——apt 是全有或全无的，一个不存在的包会让
整条命令里后面的包一起装不上。同时标注：本仓库实际用 `gmapping` / `slam_karto`
（+ hector 可选）已够覆盖复赛建图需求，Cartographer 属加分项。

## #2 红绿灯验证与循环节点争抢

**根因**：`tools/verify_traffic_light.py` 自己写 `/gazebo/set_model_configuration`
强制设关节，而 `competition_arena/scripts/traffic_light.py` 每 0.2 s tick 一次、
状态变化时也写同一组关节。强设后固定 `sleep(0.7)` 就测量 → 撞上循环切换就被覆盖，
表现为"6 次里偶尔错 1 次"。

**修法**（比"先冻结节点"更进一步）：
1. 验证脚本改为**通过 `/traffic_light/command` 命令切换节点** —— 让节点成为唯一写入者，
   顺带把"节点 → Gazebo"整条链也验了；节点不在时才退回直接写，并打印风险提示。
2. 判定从固定 sleep 改成**轮询到灯珠位姿稳定**为止。
3. 测完把状态交还 `auto`，并**新增自动循环检查**：订阅 `/traffic_light/state`，
   观察 22 s 内应出现 ≥2 种颜色 —— 这样"循环节点本身在工作"也被覆盖
   （原来那个故障模式会被漏掉）。

**实测**：连续两轮 **6/6**；自动循环 22 s 内观察到 `green, yellow, red` ✓

## #3 验收第 3 项采不到 `/amcl_pose`

**根因**：`amcl_params.yaml` 的 `update_min_d: 0.05 / update_min_a: 0.1` 表示
"车移动超过 5 cm / 转超过 0.1 rad 才更新滤波器"。车在出生点静置 → 不更新 →
**不发 `/amcl_pose`** → `check_localization.py` 一条样本都收不到。

**修法**：**不动 AMCL**，改数据源 —— `check_localization.py` 改为用
**TF `map → base_footprint`** 取定位位姿（AMCL 持续维护这条变换，静止也有值），
由 `/odom_groundtruth` 驱动采样并限速 10 Hz；`/amcl_pose` 只作兜底与诊断
（csv 里多一列 `src`）。另加兜底：6 s 没样本就原地轻转一下。

**实测**：静止时 **199 条配对（TF 218 / amcl 9）**，采样率 8 Hz，位置误差 0.0134 m ✓

> ⚠️ 关联 #7：**不要**为了"静止时也能采到"去把 `update_min_d/a` 设成 0.0。

## #4 WSL 下 RViz 看不到车模（用户已修）

**判据**：激光点能正常显示 ⇒ `map→odom→base_footprint→base_link→laser_link`
整条 TF 是通的 ⇒ 不是 TF，而是**网格渲染**问题。STL 有效性、材质 alpha、RViz 配置都排除过。

**根因**：WSLg 的 Mesa `d3d12` gallium 驱动在 OGRE 网格渲染上的缺陷
（WSL 里没有 Linux NVIDIA 驱动，OpenGL 走 d3d12 → `/dev/dxg` → Windows 驱动）。

**修法**（`78d5358`）：`navigation_wsl.launch` —— 只给 **RViz 这一个进程**设
`LIBGL_ALWAYS_SOFTWARE=1`，Gazebo 保持 GPU 加速。

**补充**：窗口标题偶现 `[WARN:COPY MODE]` 是同一套栈退化成 CPU 逐帧拷贝，
先 `wsl --shutdown`、只开一个界面可缓解（已写进 `docs/wsl_setup.md`）。

## #5 导航帧率 60 → 10（world 缺 `<physics>`）

**根因**：`competition_arena.world` 没有 `<physics>`，Gazebo 用内置默认
`max_step_size = 0.001`（1000 Hz）。场地小/模型少时勉强跟得上，
这次加了 14 个模型（10 立牌 + 3 车 + 红绿灯）并外扩 → 算不过来，RTF 掉到 0.80，
界面帧率跟着崩。**旧 world 也没有 physics 段**，所以不是这次更新弄丢的配置。

**修法**：`build_arena.py` 的 world 模板里插入 `<physics>`（type=ode, quick solver），
并加 `--max-step-size` 参数（默认 **0.002 = 500 Hz**），world 文件同步更新。
0.004/250 Hz 或 0.008/125 Hz 更省 CPU，适合只看画面/录制。

**实测**（本沙箱无 GPU）：RTF **0.66 → 1.14**；用户机上有 GPU：0.797 → 1.000。

> ⚠️ 步长变大会影响接触/摩擦精度，而仓库里大量实测结论基于旧步长。
> 改完应重跑 `tools/bench_nav.sh` / `bench_slam.sh` / `bench_rtf.sh`。
> （17 站落点复测已确认导航精度没退化，见 #7。）

## #7 导航落点退化（两层根因）

### 第一层：误改 AMCL 更新阈值（本 issue 正文）

`d7e6580` 为修 #3 把 `update_min_d/a` 改成 `0.0` → AMCL **每帧激光都更新+重采样**
（10 Hz 激光 / `resample_interval: 3` → 每秒重采样约 3 次）→ 粒子集过早收敛、
丢多样性 → 系统性偏差变大。

| 配置 | 真值误差 均值 / 最大 |
|---|---|
| 文档基线 | 0.113 / 0.187 |
| `0.0`（退化） | 0.155 / 0.280（+81% / +103%） |
| **撤销回 0.05 / 0.1** | **0.122 / 0.202** ✓ |

**教训**：#3 的问题是"**测量工具**采不到数据"，我却去改了**被测量的系统**。
这类问题应先改观测方式（换数据源），不要动被测对象的参数。

### 第二层：`laser_wall_pose` 的 `inner` 没跟外扩更新（验收时新发现）

场地外扩后围墙内表面在 **±2.176 m**，但 `tools/patrol.py` 的
`laser_wall_pose(inner=2.076)` 还是旧场地的值 —— 差 **100 mm**。
用错墙面位置反推位姿 → **纯平移偏差**，实测 `(-0.0982, -0.0998) m`
（与 inner 之差完全对应）。而倒车入库的 `pose_servo` 正是用这个位姿。

**关键点**：它一直被"激光反推误差只有 1 cm"掩盖着 —— 那个指标量的是**自洽性**，
不是与真值的偏差。**参数错了却看起来很好**，比直接报错更危险。

| | 中位 | 最大 | 对比 AMCL |
|---|---|---|---|
| 修复前 | 140.1 mm | 141.6 mm | 准 0.1 倍 |
| **修复后** | **1.6 mm** | **2.8 mm** | 准 8.6 倍 |

倒车入库真值误差 **0.1323 m → 0.0120 m**（回到 1.03~1.08 cm 基线）。

**同类常量扫尾**：`check_scan_geometry.py` / `check_scan_selfhit.py` 同步改为 2.176；
`tools/map_pixels.py` 的 `INNER=2.076` 与 `gen_recognition_points.py` 的
`FIELD_LINE=2.075` 是**白线**语义（可行驶边界/不压线判定），应当保持不动。

## 这类问题的共同教训

1. **"量程"和"裁剪/边界"是两回事**，别图省事共用一份参数
   （相机 `range` vs `clip` 那次导致了 0.6 m 内目标完全不渲染）。
2. **改了场地尺寸，所有写死的边界常量都要过一遍**
   （#7 第二层就是漏了一个 `inner`）。
3. **自洽性指标不能替代真值**：激光对墙 1 cm 的"精度"掩盖了 100 mm 的系统偏差。
4. **修测量问题不要改被测量的系统**（#3 → #7 第一层）。
5. **验收脚本本身也要被验收**：验的是哪条路线、门槛 grep 的格式还存不存在
   （#6 的"验收测错对象 + 精度门槛从未生效"）。

## #8 数据集 points 模式只有 ~60% 拍到目标

**根因**：`--points-jitter 0.30` / `--points-yaw 25` 是**全局固定值**，但各点位的
`shot_distance_m` 差一倍（立牌 0.50 / 车 0.70 / 灯 1.00 m）。立牌宽仅 6.6 cm，
0.5 m 处 25° 抖动 = 横移 **0.23 m ≈ 3.5 个立牌宽** → 直接出画。
所以"漏"的全是最近的立牌点（A_north 0/3），远的车/灯反而正常。

**修法（三条一起）**：

1. **抖动按拍摄距离缩放**：`--points-jitter` / `--points-yaw` 默认改当**比例**
   （0.20 → 位置 ±0.20×距离、朝向 ±atan(0.20)=11.3°；固定角度天然对应
   "横移 = 距离的 20%"）。要旧语义加 `--jitter-abs`。
2. **目标必须在画面里**：points 模式重抽到位姿能看到对应目标为止
   （拍不到就退回点位本身），保证 `scenario` 字段可信、**按点位评估**才有意义。
3. **新增 `near` 模式**（替代默认里的 `random`）：在某个物体周围 0.4~2.5 m
   随机取位姿并朝向它 —— issue 里附带发现①"纯 random 大部分帧是背景"，现在
   这部分预算**每帧都有目标**；空帧只由 `neg` 模式产出（10%）。

**实测（`--dry-run`，不用起仿真）**：

| 配置 | 目标命中率 | 实际达成幅度 |
|---|---|---|
| 旧语义 0.30 m / 25°（`--jitter-abs`） | 62%（A_north 0/3） | — |
| **新默认（比例 0.20）** | **100%（10/10 点位各 12/12）** | 位移中位 0.090 m / 朝向中位 4.3° |
| 比例 0.40（想更大的包线） | 100% | 位移中位 0.169 m / 朝向中位 10.5° |

> 注意语义变化：**抖动现在是"上限"**——因为目标必须可见，实际落点会小一些
> （所以 `--dry-run` 会打印"实际达成幅度"，别拿请求值当包线）。
> 空帧占比也从 19% 降到 10%（`near` 不再浪费预算）。

**教训**：任何"固定容差"都要先问一句"它作用在什么尺度上"。这里目标宽度 6.6 cm、
拍摄距离 0.5~1.0 m，两者都远小于固定容差，于是容差本身成了主导误差项。

## #9 YOLO 训练跑完但收尾 val 崩掉（matplotlib 被系统版遮蔽）

**现象**：`model.train(...)` 全程正常 —— 100 epoch 跑完、打出
`Optimizer stripped from .../best.pt`，权重也落盘了；但紧接着的 `model.val()` 抛

```
AttributeError: 'FontManager' object has no attribute 'addfont'
  File ".../ultralytics/utils/metrics.py", line 880, in ap_per_class
    plot_pr_curve(x, prec_values, ap, save_dir / f"{prefix}PR_curve.png", ...)
```

很容易误判成"训练本身有问题"，其实训练完全没问题，是**画图库太老**。

**根因**：`.venv` 是 `--system-site-packages`（为了让 `rospy` / `cv_bridge` 可见），
于是系统 dist-packages 的老版本会**遮蔽** venv 版本。`setup_vision_env.sh` 里
`pip install ... matplotlib ...` 因为系统已经有 matplotlib 3.1.2，pip 认为
"Requirement already satisfied" 就不装了 —— ultralytics 8.4 要的是 **>=3.3**。

同一个遮蔽问题还波及另三个包：

| 包 | 系统版 | 要求 | 后果 |
|---|---|---|---|
| matplotlib | 3.1.2 | >=3.3 | **硬崩**（本 issue） |
| Pillow | 7.0.0 | >=7.1.0 | 潜伏 |
| requests | 2.22.0 | >=2.23.0 | 潜伏 |
| numpy | 1.17.4 | >=1.23 | 之前已修（numpy==1.24.4） |

**关键**：只看 `matplotlib.__version__` 看不出来 —— 得看 `__file__` 来自
`/.venv/` 还是 `/usr/lib/python3/dist-packages/`。

**修法**：

1. 显式钉版本，让 pip 必须装进 venv：
   `matplotlib==3.7.5`、`Pillow==9.5.0`、`requests==2.32.3`
   （3.7.5 是 py3.8 最后一版；Pillow 故意不用 10.x —— 10 删了 `Image.ANTIALIAS`
   这类老 API，hyperlpr3 还在用）。
2. `tools/setup_vision_env.sh` 的自检改成**连来源目录一起打印 + 判最低版本**，
   不达标的直接标 `FAIL`。这是防复发的关键：不然换台机器重建又会踩。
3. 实测 `tools/plate_ocr.py --selftest` 升级后仍是 **3/3**，无回归。

**验证**：修完 `val(plots=True)` 正常产出 6 张图
（`BoxPR_curve.png` / `BoxF1_curve.png` / `confusion_matrix*.png` …），
`mAP50 = 0.803`。

**教训**：`--system-site-packages` 会让"装依赖"这一步**静默失效**。凡是
"系统里也有同名包"的依赖（numpy / matplotlib / Pillow / requests / PyYAML），
都必须钉版本；并且自检要同时看**版本**和**来源路径**，只看版本会漏。

## #10 合成数据集几何框系统性偏上（车牌 OCR 端到端 0/37）

**现象**：把「YOLO 框车牌 → 裁剪 → HyperLPR3 读字符」串起来跑（`tools/detect_ocr.py`），
检测端 37/37 全中、置信度 0.93~0.98，但**字符识别 0/37 全错**，
输出的是 `晋`、`晋辽` 这种毫无意义的单字，置信度还只有 0.3。

一开始怀疑 OCR，排掉之后才定位到标签：

| 排查 | 结果 |
|---|---|
| 识别网络本身 | 喂**合成车牌** → 3/3 正确（`京A12345` @ 0.929），没坏 |
| 检测框尺寸 | 与标签框一致到 1~3 px，检测没问题 |
| 裁剪处各种预处理（归一化 / gamma / CLAHE / Otsu / 放大 1~4×） | 仍然 0/37 |
| **把 GT 框画回原图** | **框整体在车牌上方，车牌几乎全在框外** |

**根因**：`meta.jsonl` 里的框是 `label_of()` 用真值位姿做几何投影算出来的，
而这个投影得到的框**整体比画面里的目标高**。用"车牌实测位置落进预测框的比例"量化：

| 假设的相机高度 | 车牌落进预测框的比例（中位） |
|---|---|
| 0.19998 m（`robot_params.yaml` 的 `mount[2]`，现在代码用的值） | **0.20** |
| 0.2175 m（把相机抬高 0.0175 m，扫描出来的最佳值） | **1.00** |

在 0.66 m 处，0.0175 m 相当于 **26 px** —— 而车牌本身只有 52 px 高，
所以框正好错开一个车牌的高度。

**为什么之前的指标全是假象**（这是本条最值得记的部分）：

- **mAP 高 ≠ 标签对**。plate mAP50 = **0.995**、R = 1.000，恰恰因为 YOLO
  是在**学标签**：标签整体偏上，它就学着整体偏上，于是"检测完美"。
  mAP 只能证明**标签自洽**，不能证明**标签正确**。
- **edge score 高也是假象**。框整体上移一个车牌高之后，框的**下边界刚好压在车牌的
  上边缘**上——那里是全图梯度最强的地方，于是"框线贴合度"分数很漂亮（4.96），
  但框里装的其实是保险杠。
- **框的 w/h = 3.04 vs 真车牌 3.14 也没用**：形状对、位置错，比值照样对。

**已排除的怀疑**（避免重复劳动）：

- `robot_gazebo.launch` 里 `-z 0.03` 的 spawn 高度**不是**原因：车是动态模型，
  落下 3 cm 后 `base_footprint` 稳定在 z ≈ 0（实测 -2.9e-06）。
- 相机在仿真里的位置**就是** 0.19998：`gz sdf -p competition_robot.urdf` 转换后，
  camera sensor 的 pose 明明白白写着 `0.14914 -0.000497 0.19998`。
- 车牌的 SDF 位置**就是** 0.1225（`BASE_T + PLATE_CZ = 0.006 + 0.1165`），
  且代码自己的投影自洽（预测 y 588.5/640.6 vs 实际存的 588.1/641.1）。
- 车身贴图 `车牌背景.png` **不含车牌**，所以画面里的车牌确实是生成的那个，
  不存在"两个车牌"。
- `PLATE_W/PLATE_H = 0.095/0.030`（比值 3.167）与真车牌 440/140（3.143）一致，
  尺寸常量没问题。

**结论**：模型与渲染之间还有约 0.0175 m 没对上，来源尚未定位（SDF 层面三者自洽，
怀疑是 Gazebo 渲染的相机存在未建模的俯仰/主点偏移，实测该偏移**与深度无关**
——按深度分桶拟合出的等效相机高度稳定在 0.2203~0.2207 m，这正是"固定俯仰/主点偏移"
的特征，而不是"某个物体 z 错了"）。

**两条修法**（需要拍板，因为会影响所有已采数据）：

1. **标定投影**：给 `label_of()` 的投影加一个标定过的竖直修正
   （等效于相机高度 0.19998 → 0.2175，或一个主点偏移），然后**重采数据集 + 重训**。
   改动最小，但引入一个经验常数，要在文档里写清来源和适用范围。
2. **把仿真相机对齐模型**：查清 Gazebo 渲染相机的实际俯仰并让它与 URDF 一致，
   使"模型=渲染"。更干净，但要动 URDF/world，且同样要重采重训。

**教训**：
- 验证自动标注，**不能只看指标好不好看**。必须①把框画回图上人眼看，
  ②量一个已知尺寸的目标（这里是车牌 9.5×3 cm 和它的真值位置）。
  我是靠端到端 OCR **0/37** 才回头发现的——**闭环指标才是照妖镜**。
- "检测 mAP 0.99" 和 "端到端可用" 之间隔着一整个几何正确性，
  中间任何一环错了，前面的漂亮数字都会掩盖它。

## #10 续（2026-09-23）：多距离实测 —— 否定"相机高度"假说

新增工具 `tools/check_projection.py`：把车传送到离目标已知距离处，拍一张，检测**亮着的
灯珠**（发光色块最不容易检错），和几何投影比 → 得到像素偏差 Δv。

**为什么要多距离**：两种根因的"距离指纹"不同 ——

| 根因 | 偏差随距离 |
|---|---|
| **相机高度**错 | Δv ∝ 1/depth（近处大、远处小） |
| **主点**（cy）偏移 | Δv 与 depth 无关（恒定像素） |

只在一个距离上调参，**很容易补错方向**（我第一版就是按单点把相机抬高了 17.5 mm ✗）。

实测（tl_top 的绿灯珠，相机到灯珠 0.8/1.4/2.2 m）：

| 距离 | Δv = 实测 − 投影 | 按"相机高度"反解 Δz | 按"目标实际高度"反解 z |
|---|---|---|---|
| 0.80 m | **−27.5 px** | +19 mm | 0.429 m |
| 1.40 m | **−7.6 px** | +9 mm | 0.419 m |
| 2.20 m | **−3.9 px** | +7 mm | **0.418 m** |

**判定**：

* 按相机高度反解得到 **19 / 9 / 7 mm，不是常数** → **不是相机高度问题** ✗
* 按目标高度反解，远距离两点一致给出 **0.418 m**（模型写 0.410）→ **是物体自己矮了 ~9 mm** ✓

**已定位的部分**：

```
standee_c01      <static>true</static>    不沉
car_1            <static>true</static>    不沉
traffic_light_h  <static>false</static>   base 8kg, 受重力 -> 会沉  ✓
```

所以**灯箱的偏差有解释了**（动态模型沉降）；
但 **车牌那 ~26 px @0.66 m 仍未定位** —— 车是 static，没有沉降可解释 ✗。

**方向（待做）**：标注/投影不要用"写进 SDF 的位姿"，而要用 Gazebo 里**实测的 link 位姿**：
启动后对每类道具量一次实际位置（沉降量），写回投影。这样静态/动态都不用猜。

**顺带一个不一致**（影响很小，但记一下）：`cars.yaml` 里 `car_1` 的 `yaw` 与
world 里 spawn 的 `3.1416` 不同。因为车牌的局部偏置只有 4 mm，位置影响 <1 cm，
但它说明"配置里的位姿"和"场景里的位姿"是两套数据源 —— 属于同一类隐患。

## #11 采集 rig 的相机低了 0.18 m（灯箱被顶出画面）

**现象**：`--rig N` 采出来的图**灯箱顶部被切**、车板顶部被切；同一套参数用完整机器人
（不加 `--rig`）却是好的 —— 所以"我明明测过能拍全"。

**根因**（两处合起来）：

* `src/competition_arena/models/collect_rig_N/model.sdf` 的相机 `<sensor>` **没有 `<pose>`**，
  相机就在**模型原点**（注释里的"离地 0.19998"只落在 `cam_body` 那个视觉方块上）。
* `tools/gen_collect_dataset.py` 传送时 z **写死 0.02**。

→ 相机实际在 **z = 0.02**，投影却按 `camz = mount[2] = 0.19998` 算，**差 0.18 m**。
目标整体被顶高，而 `--frame-margin` 守卫用的正是这个偏掉的投影，所以拦不住。

**为什么完整机器人没事**：它有重力，落到 `base_footprint` z≈0 后相机正好在 0.19998；
rig 关了重力，就停在 0.02 不动。

**实测**（`collect_light`，灯珠顶部行像素，0~2 就是被切）：

| 距离 | 修前 | 修后 |
|---|---|---|
| 1.00 m | **0 ~ 67（被切）** | 159 ~ 177 ✓ |
| 1.25 m | 62 ~ 147 | 226 ~ 240 ✓ |
| 2.00 m | 225 ~ 285 | 324 ~ 330 ✓ |

**修法**（一行）：

```python
z = rob['mount'][2] if args.rig else 0.02   # rig 的相机在模型原点 -> 原点抬到相机高度
```

**教训**：同一个"相机"有**两套几何来源**（SDF 里的位姿 vs 采集器假设的高度），只要不一致，
取景就是错的，而且**投影守卫会跟着一起错**。自检口径应是"量画面里目标的位置"。

## #12 红绿灯模型（检灯珠）的适用包线

**模型**：`weights/traffic_light_yolo11n.pt`（yolo11n，3 类 `red_light`/`yellow_light`/`green_light`），
检的是**亮着的那一颗灯珠**，一帧通常 1 个框 → 框的类别就是状态。工具 `tools/traffic_light_yolo.py`。

**训练数据**：`light_20260923_200325`，就是我拍的 `datasets/collect_light` 那 90 张
（文件名 90/90 重合，72 train / 18 val）。训练日志：**P 0.987 / R 1.000 / mAP50 0.995**。

**测试**：

| 数据 | 结果 | 说明 |
|---|---|---|
| `collect_light` 90 张 | **90/90 = 100%** | **这就是训练集**，不能当泛化指标 |
| 比赛场地 600 帧（独立） | 435 帧没拍到灯（无事可做）；灯在画面里的 229 帧 **145/229 = 63%** | 147 次检出只有 **2 次错** → precision≈99%，**卡在 recall** |

按场地：`tl_bot` / `A_north` / `B_north` **100%**，但 **`A_south` 0/22、`A_west` 1/16**（全漏）。

**原因**：灯的采集是 2 灯 × 3 态 × 5 距离、每个姿态只抖 ±6° 偏航，**全是正对**，
没有角度和尺度的多样性 —— 竞技场里灯是斜的、远近不一，就漏了。

**要提升**：给灯加多视角（像立牌圈那样）、或者把竞技场那 229 帧也标上一起训。

**教训**：**"训练集 = 测试集"会给出 100% 的假象**。这次是靠比对文件名才发现的
（90/90 重合）。以后拿模型出来测，第一件事先确认测试集和训练集有没有重叠。

## #13 识别到黄灯还继续直走 —— 红绿灯只有"识别"没有"动作"

**现象**：实测跑一圈，识别到黄灯之后车照直走。红灯/绿灯也一样，**灯态只是打印出来**。

**两个根因**（缺一个都还是闯红灯）：

1. **`patrol.ask_vision` 拿到结果只 `rospy.loginfo` 打印**，没有任何分支去决定"该不该走"。
   灯态纯粹是日志。
2. **路线顺序**：`recognition_route.yaml` 按"沿环线弧长"排，同地点的
   `10_tl_bot`(灯) 排在 `11_B_east`(人偶) **前面**。就算补上闸，流程也是
   "判灯 -> 等绿 -> 再做别的活 -> 走"，而灯循环是 **绿6s/黄2s/红6s** ——
   干完别的活灯早变了。**闸必须放在离开路口之前的最后一步。**

**修法**：

* `tools/patrol.py` 加 `light_gate()`：
  * 红灯 / 黄灯 -> **原地停车等待**，每隔 `--light-recheck`(默认1.5s) 重看一次
  * 没看到灯 -> 当作"不能通行"同样等待（**不能"看不见就默认走"**）
  * 绿灯 -> **连续 `--light-confirm`(默认2) 次**都读到绿灯才放行（防单帧误检）
  * 等超过 `--light-max-wait`(默认60s) 仍未确认 -> **停车并结束本次运行**（不倒车入库）；
    要放行得显式 `--light-none-go`
  * `--no-light-gate` 可关掉（调试用）
* `tools/gen_recognition_route.py` 加 `_gate_last()`：把每个红绿灯挪到
  **跟它同地点那一组站点的最后**（`GATE_R=0.30`；10/11 相距 0.082 m，而离前后
  邻站最近 0.61 m，所以 0.30 能干净切出这一组）。重新生成后路线变成
  `10_B_east`(人偶) -> `11_tl_bot`(灯)，**其它站一字未动**（diff 确认过）。

**实测**：

| 用例 | 结果 |
|---|---|
| 单元（7 个分支：红/黄/看不到/红转绿/只绿一帧/--light-none-go/--no-light-gate）| **7/7** |
| 集成·强制**红灯**跑 mini 路线 | `红灯 -> 原地停车等待(已等0/4/8/12s)` -> `等了12s仍没确认绿灯 -> 停车，本次运行结束` ✓ |
| 集成·强制**绿灯** | `绿灯(1/2次确认)` -> `绿灯(连续2次确认)->放行` -> `一圈跑完: 1/1` ✓ |
| 集成·强制**黄灯** | `黄灯 -> 原地停车等待` -> 停车 ✓ |

**教训**：**"识别出来"和"按它行动"是两件事。** 模型/节点输出只是信息，
必须有人把它接成控制逻辑；而这条链里还有个隐蔽的时间问题 ——
**判据的时效性**（先判后干别的活 = 判据过期）。凡是"闸"，都要放在它约束的那个动作**紧前面**。
